## Context

The CRM Frontier Firm Showcase runs against a Microsoft-provided demo tenant with
two Power Platform environments (`DEV`, `TEST`). CI, automation, and — where a story
scopes it — Copilot Studio agents need to authenticate to that tenant to:

- Deploy Dataverse solutions and Power Platform artefacts.
- Read/write Dataverse records for tests.
- Read Microsoft Graph for personas / demo data seeding.

A shortcut option was raised: give GitHub Copilot / automation a **Global Admin UPN**
of the demo tenant and let it "read, manage, update, and configure any artefacts."

That option is rejected. Reasons:

1. **Every rule in [SUPERPOWERS_CONTRACT.md](../../SUPERPOWERS_CONTRACT.md) §1.2, §1.4
   and [docs/SECURITY.md](../SECURITY.md) §1** forbids storing credentials or wiring
   an unbounded identity into the tenant.
2. **A UPN paired with any auth material** (password, PAT, client secret) becomes a
   secret. Even the UPN alone becomes a phishing / password-spray target when
   published.
3. **"Manage anything"** violates least-privilege. A CI job that deploys a Dataverse
   solution does not need permission to reset user MFA or read another tenant's mail.
4. **The repo is public.** Any identifier or secret in the repo is world-readable and
   search-indexed on push.

## Decision

Adopt **Entra ID workload identity federation** (OIDC) as the single auth pattern
between GitHub Actions and the demo tenant, plus **interactive Entra sign-in** for
local dev.

Concretely:

1. Create **one Entra App Registration per environment slot** (`crm-showcase-ci-dev`,
   `crm-showcase-ci-test`). No shared app across environments.
2. Configure **federated credentials** on each app for the GitHub repo
   `urruegg/CRMShowcase`, scoped to the matching GitHub **Environment**
   (`dev`, `test`) and to specific refs (`main` or release branches).
3. **No client secret** is created for these apps. Ever. Federation replaces it.
4. Grant each app **only the roles the CI job actually uses** in its target
   environment (e.g., Dataverse system-customizer, not System Administrator; specific
   Graph application permissions only when a story requires them).
5. In GitHub Actions, use the official `azure/login` action with `federated-token` or
   the Power Platform CLI action's OIDC mode. Never `client-secret` mode.
6. Any incidental secret (e.g., a webhook signing key generated by a story) lives in
   **Azure Key Vault** in the demo tenant and is fetched at runtime via the same
   workload identity.
7. For **local dev**, developers sign in interactively with `az login` /
   Power Platform CLI. No stored credential, no shared account.
8. **The tenant Global Admin UPN is never used** for CI, automation, or Copilot.
   Global Admin is human-only, MFA-enforced, and used only for the manual
   provisioning of the app registrations in step 1.

## Consequences

**Positive**
- No secret exists to leak — federation is short-lived and scope-bound.
- Every CI action is auditable to a specific app registration and a specific
  federated subject (repo + environment + ref).
- Least-privilege by design: adding a permission requires an ADR update.
- Aligns with [SUPERPOWERS_CONTRACT.md](../../SUPERPOWERS_CONTRACT.md) §1.2 and §1.4
  and with [docs/SECURITY.md](../SECURITY.md).

**Negative / cost**
- Two Entra app registrations to provision manually before CI can deploy anything.
- Federated credential subjects must be updated if the repo is renamed or the
  environment slots change.
- Developers must sign in interactively for local dev — no "just paste the password".

**Follow-ups**
- Provision `crm-showcase-ci-dev` and `crm-showcase-ci-test` app registrations
  (repo owner, out-of-band).
- Add matching **GitHub Environments** (`dev`, `test`) with required reviewers on `test`.
- When the first CI deploy story lands, add a workflow using `azure/login` OIDC and
  reference this ADR in the PR.
